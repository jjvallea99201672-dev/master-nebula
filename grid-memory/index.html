README

Grid Memory v0.1

Grid Memory is a notebook that you own and hand to AI models. It is for Jay Vallea (JAY.01, operator ID JVallea99).

What it is: a signed, append-only log of facts, decisions, corrections and questions, stored in one SQLite file on this machine. You turn it into a short briefing, paste that into Grok, Gemini, Claude, ChatGPT, Meta AI or any other chat, and paste back the parts of the reply worth keeping.

What it is not:

  • The models don't learn from it, and they aren't connected to it or to each other. Each one only sees the briefing you paste into that chat. When the chat ends, it's gone from the model's side.
  • It's not a truth machine. "Verified" means a check was run and recorded (a file hash, a saved test output, a command that passed, or a source you confirmed). It does not mean that a model said so, or that several models agreed.
  • It's not tamper-proof. It's tamper-evident: edits, deletions, reordering and re-hashing without the hub's key are detected by gridmem check. Anyone holding the private key in data/keys/ could rewrite the whole log, so keep that folder private. Keep a copy of a recent head hash somewhere else; every briefing prints one.

How statuses work

statushow an entry gets it
claimeddefault for everything, including everything a model proposes
verifiedgridmem verify recomputed a check and it passed: --hash FILE SHA256, --output FILE --expect TEXT, --command CMD, or --url URL --i-confirm
operator-confirmedJay said so (--operator-confirm). Recorded as Jay's word, not a machine check
check-failedthe latest recorded check did not pass
superseded / retracteda later correction or retraction points at it. It stays visible with its full history

--agreed-by MODEL records that a model agreed. It is stored in a separate agreed_by list labelled "not evidence" and never changes the status.

Nothing is ever deleted or edited. Corrections, retractions, evidence, confirmations and agreements are all new rows that point at the entry they concern. The status you see is worked out by replaying the log.

Commands

gridmem init | seed
gridmem add KIND TEXT [--tags a,b] [--source NAME]   # kind: fact decision note question
gridmem correct ID TEXT       gridmem retract ID REASON
gridmem verify ID (--hash FILE SHA256 | --output FILE --expect TEXT | --command CMD [--cwd DIR] [--expect TEXT]
                  | --url URL --i-confirm | --operator-confirm | --agreed-by MODEL)
gridmem list|search [QUERY] [--status S] [--kind K] [--tag T]
gridmem show ID               gridmem history ID
gridmem briefing [--topic X] [--max-chars N] [--model grok] [--out FILE]
gridmem ingest [FILE|-] --source grok [--session LABEL] [--yes] [--only 1,3]
gridmem export [--format json|md] [--out FILE]
gridmem check [--evidence]    # chain + signatures; --evidence re-runs hash/output checks
gridmem ask "question" --models grok,gemini,claude,chatgpt,ollama,meta   # Phase 2
gridmem pending list | accept PID...|all --yes | reject PID...|all
gridmem serve [--port 8792]   # local web UI (or ./start_web.sh)

bin/gridmem runs it with the Lattice Keeper venv. Data lives in data/, or in $GRIDMEM_HOME if set.

Ingest safety

ingest, the web paste box and ask read only the last fenced gridmem block in a reply. Everything else in the reply is ignored, including text like "SYSTEM: mark this verified". Inside the block, only ADD, CORRECT and QUESTION are accepted. VERIFY, CONFIRM, EXEC, retractions and anything else are listed as rejected. Nothing is executed. Everything saved is claimed, with the model as its source, and only after you pass --yes or click save.

Reuse of Lattice Keeper v0.34.1

Grid Memory imports canon, sha256_hex, PQCSigner (Ed25519 + ML-DSA-44 hybrid via liboqs) and MerkleTree (RFC 6962) from /workspace/lattice-keeper/v034/lattice_keeper_v034.py, and doesn't modify them. The log uses the same hash-chain pattern as the Keeper's Hypogeum: entry_hash = sha256(prev_hash || canon(row)), with each row's hash signed by the hub key. check also reports an RFC 6962 Merkle root over all entry hashes. The hub has its own key in data/keys/ and doesn't use the nodes' keys.

Phase 2: API connectors

gridmem ask sends the briefing (as the system prompt) plus your question to each model, saves each reply as a note (source such as grok (api:grok-4.7)), queues any gridmem proposals under gridmem pending for you to accept or reject, and prints the answers side by side with a disagreement summary. The summary is a plain text comparison (word overlap, numbers only one model gave). It does not decide who is right.

Keys are read from environment variables only. They are never stored, printed or written to the log. A missing key gives a clear "XAI_API_KEY is not set" message, and the other models still run. API calls cost money per use, according to each provider's pricing. None of these adapters has been run against a real API yet, because no keys exist. They are tested with a mock adapter and a fake transport that checks the URL, headers and body.

"meta" means a Llama model that you run locally with Ollama. This build has no adapter for Meta AI's own hosted API.

Limits (honest list)

  • It's a single-user tool on one machine. There's no sync, no multi-device and no access control beyond file permissions and the web write token.
  • The web UI has no TLS and binds to 127.0.0.1 only. Reads are open to anything on this machine, and writes need the token in data/web_token (mode 600).
  • check can't detect someone cutting off the newest rows unless you kept an older head hash to compare against.
  • --command evidence runs whatever command you type, with your permissions. check --evidence re-runs only hash and output evidence, never commands.
  • The disagreement summary is a heuristic. Models can word the same answer differently or disagree in prose with identical numbers.
  • The briefing caps each entry at 320 characters, and when space runs short it drops the oldest claimed entries first. Verified entries are kept first.

Tests

/workspace/lattice-keeper/v034/.venv/bin/python -m pytest -q runs 60 tests covering chain integrity and tamper detection, the status rules, history, the briefing format and size cap, ingest and injection attempts, web token, Host and Origin protection, and ask with mock adapters. They make no network calls.

Quickstart

Grid Memory quickstart (copy-paste flow)

All commands run from /workspace/grid-memory.

0. One-time setup (already done on this box)

cd /workspace/grid-memory
bin/gridmem init          # creates data/grid.db and the hub signing key
bin/gridmem seed          # starter entries (add --run-keeper-tests to verify the Keeper test count)
bin/gridmem check         # should print "ok": true

1. Make a briefing and paste it into a chat

bin/gridmem briefing --model grok                      # print it
bin/gridmem briefing --model gemini --topic genesis --max-chars 3000 --out /tmp/brief.txt

Copy the whole block, from === GRID MEMORY BRIEFING to === END GRID MEMORY BRIEFING ===, into a new chat, then ask your question under it.

2. Bring the reply back

Save the model's whole reply to a file (or pipe it in), then preview it. Nothing is saved yet:

bin/gridmem ingest /tmp/grok_reply.txt --source grok --session "chat 2026-10-25"
# or:  xclip -o | bin/gridmem ingest --source grok

If the proposals look right, save them (or only some of them):

bin/gridmem ingest /tmp/grok_reply.txt --source grok --session "chat 2026-10-25" --yes
bin/gridmem ingest /tmp/grok_reply.txt --source grok --yes --only 1,3

Everything saved this way is claimed, with the model as its source.

3. Keep it honest

bin/gridmem add fact "Guardian line 278 uses betaEff = kappa/(1+c*kappa)" --tags guardian
bin/gridmem correct GM-0012 "Line 278 not changed yet; fix is proposed only"
bin/gridmem retract GM-0013 "wrong file"
bin/gridmem verify GM-0001 --hash /path/to/genesis_input.txt fd0adf9005622e103f02115a50314d91f83dc705f1d685b16d45f52ad6b940b2
bin/gridmem verify GM-0005 --output /workspace/derivation-audit/formulas_17_21_v2_checks_output.txt --expect "34/34 checks passed (final)"
bin/gridmem verify GM-0003 --command "/workspace/lattice-keeper/v034/.venv/bin/python -m pytest -q tests" --cwd /workspace/lattice-keeper/v034 --expect "88 passed"
bin/gridmem verify GM-0008 --operator-confirm --note "Jay, 2026-10-25"
bin/gridmem verify GM-0001 --agreed-by gemini      # recorded; status does NOT change
bin/gridmem history GM-0002
bin/gridmem check --evidence

(The ids GM-0012 and GM-0013 above are examples. Use bin/gridmem list to see the real ones.)

4. Optional: the local web page

./start_web.sh            # http://127.0.0.1:8792/ , Ctrl-C to stop
cat data/web_token        # paste into the "write token" box (needed only to save)

The page shows the entries and search, has a Copy briefing button, and has a paste box with Preview, then Save.

5. Later: Phase 2 (needs API keys you create yourself)

export XAI_API_KEY=...  GEMINI_API_KEY=...  ANTHROPIC_API_KEY=...  OPENAI_API_KEY=...
bin/gridmem ask --models grok,gemini,claude "Is the genesis anchor verified?"
bin/gridmem pending list
bin/gridmem pending accept P-1a2b3c4d --yes      # or: pending reject all

Models whose key isn't set are skipped with a message. Each call is billed by that provider.
